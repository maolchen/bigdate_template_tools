# 需求设计文档

## 1. 项目定位

`bigdate_template_tools` 是一个内部使用的离线交付工具，用于通过结构化配置和模板，生成可直接部署的大数据平台服务脚本与配置文件。

工具解决的问题：

- 统一管理多服务、多节点的部署参数
- 降低重复交付时的人工修改成本
- 让模板维护、配置维护、输出生成三件事拆开管理
- 让多用户在同一台服务器上并行使用时尽量互不影响

## 2. 当前业务目标

### 2.1 配置侧

支持交付人员通过 Web 页面维护：

- 全局配置 `global`
- 节点池 `nodes`
- 服务拓扑 `serviceTop`
- 服务配置 `serverConfig`

并把这些配置保存回 YAML 文件。

### 2.2 模板侧

支持通过两种方式维护模板：

- AI 模板工作台：对话生成模板草稿，再保存到 `templates/`
- 模板编辑器：直接在线查看和编辑 `templates/`

### 2.3 生成侧

根据配置与模板生成：

- 安装脚本
- 启停脚本
- 检查脚本
- 配置文件

输出目录可直接给交付人员使用。

## 3. 当前实现方案

### 3.1 多用户并发方案

当前已落地的是“最简内部版”方案：

- 引入登录功能
- 用户角色分为：
  - `admin`
  - `user`
- 管理员同一时刻仅允许一个会话
- 每个用户拥有自己的配置空间与输出空间

### 3.2 用户空间隔离

每个用户登录后使用自己的配置副本，而不是直接编辑根目录 `config.yaml`。

用户空间目录：

```text
data/users/<username>/
├── configs/
│   ├── config.yaml
│   ├── <id>_config.yaml
│   └── templates_index.json
└── meta.json
```

规则：

- 用户首次登录时，如果 `data/users/<username>/configs/config.yaml` 不存在，则从根 `config.yaml` 复制一份
- 如果已经存在，则直接使用，不覆盖
- 用户所有配置编辑都作用于自己当前主模板对应的 YAML 文件

### 3.3 配置模板管理

每个用户可以保留多份完整 YAML 副本作为“配置模板”。

表现规则：

- 主模板固定表现为 `config.yaml`
- 备份模板文件名为 `<id>_config.yaml`
- 切换模板不是简单修改指针，而是执行主模板与目标备份模板的文件互换
- 这样可以始终保证当前正在编辑的是 `config.yaml`

### 3.4 根配置同步策略

根目录 `config.yaml` 仍然是系统级主配置基线。

用户空间与主配置的同步策略：

- 触发时机：
  - 用户登录后感知版本变化
  - 用户主动点击同步
- 默认同步内容：
  - 全局配置中的新增 key
  - `serviceTop` 中新增服务
  - `serverConfig` 中新增服务
- 默认不同步内容：
  - 已存在字段的覆盖更新
  - 删除项

另外提供危险操作：

- 按主配置清理删除项
- 用于把用户空间中主配置已删除的项也同步清理掉

### 3.5 输出隔离

生成输出按用户隔离：

```text
output/users/<username>/...
```

避免不同用户生成结果互相覆盖。

## 4. 权限模型

### 4.1 admin

管理员拥有：

- 登录系统
- 查看/编辑所有配置页面
- AI 模板保存到 `templates/`
- 模板编辑器写权限
- 用户管理
- 修改密码

### 4.2 user

普通用户拥有：

- 登录系统
- 查看/编辑自己的配置空间
- 使用 AI 模板生成草稿
- 查看模板编辑器
- 不能保存模板到 `templates/`
- 不能修改模板目录结构
- 不能进入用户管理

## 5. 配置模型

配置核心结构：

### 5.1 global

全局公共变量，例如：

- 用户名/组名
- 安装目录
- 数据目录
- 软件目录
- Java 路径

特点：

- 动态 KV 结构
- 可以新增和删除 key
- 主配置新增 key 可以同步到用户空间

### 5.2 nodes

节点池定义：

- `ip`
- `hostname`

特点：

- 节点名是逻辑别名
- `serviceTop` 通过节点名引用节点

### 5.3 serviceTop

服务拓扑定义：

- 服务部署到哪些节点
- 是否自动推导 ID

特点：

- 决定服务实例如何展开
- 是渲染阶段的实例生成依据

### 5.4 serverConfig

服务配置定义：

- `type`
- `description`
- `id_field`
- `id_format`
- `vars`

特点：

- `vars` 是动态键值对
- 模板中大量通过 `.Instance.Vars.xxx` 使用

### 5.5 nodeOverrides

节点特化配置：

- 用于对单节点、单服务做变量覆盖

## 6. 模板模型

正式模板目录：

```text
templates/<service>/*.tmpl
```

当前未做模板版本库，仍直接使用文件系统目录作为正式模板源。

### 6.1 模板输入上下文

运行时使用 `config.Context`：

- `.Global`
- `.Nodes`
- `.Instance`
- `.AllInstances`

### 6.2 模板输出目录

输出结构：

```text
output/users/<username>/<nodeIP>/<service>/<file>
```

## 7. AI 模板工作台

### 7.1 当前职责

AI 工作台负责：

- 管理会话
- 上传文本/图片附件
- 选择 skill
- 发送消息给模型
- 接收结构化返回
- 展示草稿、计划动作、配置补丁与问题
- 保存审核通过的模板

### 7.2 AI 输出协议

当前后端要求模型输出 JSON 结构，核心字段包括：

- `assistantMessage`
- `draftFiles[]`
- `plannedActions[]`
- `warnings[]`
- `followUpQuestions[]`
- `configPatch`

### 7.3 保存逻辑

AI 保存模板时：

1. 仅管理员允许执行
2. 先校验模板语法与模板约束
3. 写入 `templates/`
4. 可选把配置补丁应用到当前配置
5. 如存在阻塞问题则拒绝同步配置，但模板文件已保存

## 8. 模板编辑器

模板编辑器是一个独立页面，接近 VSCode 的 Web 化编辑器。

当前支持：

- 目录树浏览
- 文件查看/编辑
- 黑白模式切换
- 根目录/子目录创建文件和目录
- 删除文件/目录
- 目录全部展开/全部收起
- 右键菜单操作

权限：

- `admin` 可写
- `user` 只读

## 9. 当前存储设计

### 9.1 文件存储

- 根配置：`config.yaml`
- 模板：`templates/`
- 用户：`data/users/users.json`
- 会话：`data/auth/sessions.json`
- 用户配置：`data/users/<username>/configs/`
- AI 会话：`data/ai/sessions/`
- AI 上传：`data/ai/uploads/`
- AI 设置：`data/ai/settings.json`
- AI 规则：`data/ai/template_rules.md`
- AI 示例索引：`data/ai/examples_index.json`

### 9.2 不采用数据库的原因

当前设计明确面向内部单机工具：

- 用户数量少
- 部署实例单一
- 文件直接可见，便于人工兜底排查
- 实现和维护成本低

## 10. 非目标

当前版本明确不做：

- 多实例部署下的分布式锁
- 模板版本发布库
- 工作区审批流
- 项目级契约系统
- 数据库化审计系统
- 复杂 RBAC 权限体系

## 11. 当前风险与限制

- 依赖文件存储，缺少数据库事务能力
- 模板正式目录仍是直接可写文件系统
- 部分历史模块仍有中文编码问题，后续需要逐步清理为 UTF-8
- AI 强依赖结构化 JSON 输出，不同模型兼容性存在差异

## 12. 后续演进建议

如果继续演进，建议按以下顺序推进：

1. 统一清理前后端源码中文编码
2. 完善 README / 接口文档 / 调用链图，保持文档与代码一致
3. 为 AI 模板工作台补更多单测与失败诊断日志
4. 若后续并发、审计要求提升，再考虑引入 SQLite
